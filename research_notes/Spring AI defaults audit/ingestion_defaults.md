## TokenTextSplitter: every builder/constructor default, tokenizer, and exact chunk-boundary behaviour

### Takeaway
`TokenTextSplitter.builder().build()` = **chunkSize 800 CL100K_BASE tokens, minChunkSizeChars 350, minChunkLengthToEmbed 5, maxNumChunks 10000, keepSeparator true, punctuationMarks `['.', '?', '!', '\n']`**. The code comment "800 tokens, as shipped" is correct. Chunking is **token-window-first, punctuation-backtrack-second**: it will split mid-sentence whenever no `. ? ! \n` occurs after character 350 of the ~800-token window, and `minChunkLengthToEmbed` is the one that **silently discards** chunks (any chunk whose trimmed length is **≤ 5 characters** is dropped with no log, no metric, no exception).

### Cited Findings
- Source file: `spring-ai-commons/src/main/java/org/springframework/ai/transformer/splitter/TokenTextSplitter.java` — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/spring-ai-commons/src/main/java/org/springframework/ai/transformer/splitter/TokenTextSplitter.java)
- Exact constants, verbatim from 2.0.1 source:
  ```java

  private static final int MIN_CHUNK_SIZE_CHARS = 350;
  private static final int MIN_CHUNK_LENGTH_TO_EMBED = 5;
  private static final int MAX_NUM_CHUNKS = 10000;
  private static final boolean KEEP_SEPARATOR = true;
  private static final List<Character> DEFAULT_PUNCTUATION_MARKS = List.of('.', '?', '!', '\n');
  private static final EncodingType DEFAULT_ENCODING_TYPE = EncodingType.CL100K_BASE;
  ```
  — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/spring-ai-commons/src/main/java/org/springframework/ai/transformer/splitter/TokenTextSplitter.java)
- The builder's field initialisers are exactly those constants (`private EncodingType encodingType = DEFAULT_ENCODING_TYPE; private int chunkSize = DEFAULT_CHUNK_SIZE; private int minChunkSizeChars = MIN_CHUNK_SIZE_CHARS; private int minChunkLengthToEmbed = MIN_CHUNK_LENGTH_TO_EMBED; private int maxNumChunks = MAX_NUM_CHUNKS; private boolean keepSeparator = KEEP_SEPARATOR; private List<Character> punctuationMarks = DEFAULT_PUNCTUATION_MARKS;`), so `builder().build()` is identical to the (now deprecated) no-arg constructor — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/spring-ai-commons/src/main/java/org/springframework/ai/transformer/splitter/TokenTextSplitter.java)

- Tokenizer: JTokkit (`com.knuddels.jtokkit`), `Encodings.newLazyEncodingRegistry().getEncoding(EncodingType.CL100K_BASE)`; chunk size is counted in **tokens of that encoding** — `getEncodedTokens(text)` = `this.encoding.encode(text).boxed()`, and the window is `tokens.subList(0, Math.min(chunkSize, tokens.size()))` — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/spring-ai-commons/src/main/java/org/springframework/ai/transformer/splitter/TokenTextSplitter.java)
- CL100K_BASE is OpenAI's `text-embedding-ada-002`/GPT-3.5–4 encoding; it is **not** the tokenizer of any Ollama embedding model, so "800 tokens" is 800 *OpenAI* tokens, not 800 tokens of the serving model — (encoding identity per JTokkit `EncodingType.CL100K_BASE`, used unconditionally by default here) — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/spring-ai-commons/src/main/java/org/springframework/ai/transformer/splitter/TokenTextSplitter.java)
- Boundary algorithm, verbatim (2.0.1 `doSplit`):
  ```java
  if (tokens.size() > chunkSize) {
      int lastPunctuation = getLastPunctuationIndex(chunkText);
      if (lastPunctuation != -1 && lastPunctuation > this.minChunkSizeChars) {
          chunkText = chunkText.substring(0, lastPunctuation + 1);
      }
  }
  String chunkTextToAppend = (this.keepSeparator) ? chunkText.trim()
          : chunkText.replace(System.lineSeparator(), " ").trim();
  if (chunkTextToAppend.length() > this.minChunkLengthToEmbed) {
      chunks.add(chunkTextToAppend);
  }
  tokens = tokens.subList(getEncodedTokens(chunkText).size(), tokens.size());
  ```
  — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/spring-ai-commons/src/main/java/org/springframework/ai/transformer/splitter/TokenTextSplitter.java)
- `getLastPunctuationIndex` takes the **maximum `lastIndexOf`** over `['.','?','!','\n']` — i.e. the *last* occurrence anywhere in the window, by character index, not a sentence parser — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/spring-ai-commons/src/main/java/org/springframework/ai/transformer/splitter/TokenTextSplitter.java)
- `minChunkSizeChars` (350) is **only** a floor on where backtracking may cut: the punctuation index must be `> 350` characters into the decoded window, otherwise the chunk is emitted **un-backtracked**, i.e. cut at the raw 800th token — mid-sentence, mid-word, mid-number. It is *not* a minimum chunk size: chunks shorter than 350 chars are emitted freely (the last chunk of any document, for one) — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/spring-ai-commons/src/main/java/org/springframework/ai/transformer/splitter/TokenTextSplitter.java)
- `minChunkLengthToEmbed` (5) is the **silent discard**, and it is a **character** count on the trimmed text, applied twice: once per emitted chunk inside the loop (`chunkTextToAppend.length() > this.minChunkLengthToEmbed`) and once on the trailing remainder (`if (remaining_text.length() > this.minChunkLengthToEmbed) chunks.add(remaining_text);`). The comparison is strict `>`, so a chunk of exactly 5 characters is dropped. There is no logging on this path — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/spring-ai-commons/src/main/java/org/springframework/ai/transformer/splitter/TokenTextSplitter.java)
- Whitespace-only windows are also dropped silently (`if (chunkText.trim().isEmpty()) { tokens = tokens.subList(chunk.size(), tokens.size()); continue; }`) — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/spring-ai-commons/src/main/java/org/springframework/ai/transformer/splitter/TokenTextSplitter.java)
- `maxNumChunks` (10000) does **not** throw and does **not** drop the tail: the `while` loop exits at 10000, then the post-loop block decodes **all remaining tokens** into one chunk and appends it if longer than 5 chars. So the failure mode of exceeding `maxNumChunks` is a single, arbitrarily large final chunk — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/spring-ai-commons/src/main/java/org/springframework/ai/transformer/splitter/TokenTextSplitter.java)
- `keepSeparator = true` means newlines are **kept** inside chunks; when `false`, only `System.lineSeparator()` is replaced with a space (platform-dependent — on macOS/Linux `"\n"`, so on Windows a `"\n"`-only document would be unaffected). Note the trailing-remainder branch applies `.replace(System.lineSeparator(), " ")` **unconditionally**, ignoring `keepSeparator` — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/spring-ai-commons/src/main/java/org/springframework/ai/transformer/splitter/TokenTextSplitter.java)
- Validation at construction: `chunkSize > 0`, `maxNumChunks > 0`, `minChunkSizeChars >= 0`, `minChunkLengthToEmbed >= 0`, `punctuationMarks` not empty — so nothing about the default combination is checked for coherence against any model's context window — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/spring-ai-commons/src/main/java/org/springframework/ai/transformer/splitter/TokenTextSplitter.java)
- Chunk metadata written by the superclass `TextSplitter` (2.0.1): every chunk inherits the parent's metadata plus `parent_document_id`, `chunk_index`, `total_chunks`; parent `score` is copied and a **new random id** is assigned per chunk; it logs only `"Splitting up document into N chunks."` at INFO when `N > 1` — `spring-ai-commons/src/main/java/org/springframework/ai/transformer/splitter/TextSplitter.java` — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/spring-ai-commons/src/main/java/org/springframework/ai/transformer/splitter/TextSplitter.java)
- These five defaults **are** documented (with the same values) in the 2.0.x reference ETL page: `chunkSize` "default: 800", `minChunkSizeChars` "default: 350", `minChunkLengthToEmbed` "default: 5", `maxNumChunks` "default: 10000", `keepSeparator` "default: true", plus `CL100K_BASE` and the punctuation list — [docs.spring.io ETL Pipeline (page served as 2.0.2)](https://docs.spring.io/spring-ai/reference/api/etl-pipeline.html)
- The docs do **not** state the boundary algorithm (that backtracking is skipped when `tokens.size() <= chunkSize`, that `minChunkSizeChars` gates backtracking rather than enforcing a minimum, that `minChunkLengthToEmbed` discards, or the `maxNumChunks` overflow-into-one-chunk behaviour). Those were read from source — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/spring-ai-commons/src/main/java/org/springframework/ai/transformer/splitter/TokenTextSplitter.java)

### Inferences
- **Mid-sentence splitting is the default outcome for prose without punctuation in the back half of the window, and the normal outcome for tabular/flattened text.** An 800-CL100K-token window is roughly 2,800–3,600 characters of English; backtracking is allowed anywhere after char 350, so for ordinary prose the cut usually lands on a sentence end. But when the window contains no `.`/`?`/`!`/`\n` after char 350 — flattened HTML tables, number runs, long headings, non-Latin text with different punctuation — the chunk is cut at the raw 800th token.
- **`.` is matched as a bare character, so decimal points and abbreviations are legal chunk boundaries.** In financial text (`"12.5%"`, `"U.S."`, `"$1.2bn"`) the last `.` in the window is frequently *inside* a number or abbreviation, so the backtrack can cut mid-number, and the next chunk then opens with the fractional part. This is a direct consequence of `lastIndexOf('.')` with no context check; I did not find a test or doc acknowledging it.
- **The discard rule is nearly harmless for prose and dangerous for short-field corpora.** Any document (or trailing fragment) whose text trims to ≤ 5 characters produces **zero** chunks — the ingestion count silently drops below the input count. With one Document per HTML file this would only ever drop a fragment; with per-element reading (`groupByElement(true)`) it would drop every short cell/heading/`<li>`.
- Token re-encoding after backtracking (`tokens.subList(getEncodedTokens(chunkText).size(), ...)`) re-tokenises the *truncated string*; because `chunkText` is a decoded-then-re-sliced string, the re-encoded prefix length is assumed to align with the original token stream. For ASCII prose this holds in practice, but it is an assumption, not an invariant — an unverified risk of off-by-a-few overlap/loss on text where decode→substring→encode is not round-trip stable (e.g. multi-byte characters whose bytes straddle the 800-token cut). Flagged as unverified; I found no test covering it.

### Gaps
- No reference-doc statement anywhere on *why* 800/350 were chosen, nor any guidance tying `chunkSize` to the serving embedding model's context window. The docs present them purely as knobs.
- I did not empirically run the splitter against the project's corpus, so the *frequency* of mid-sentence cuts in this corpus is unmeasured (it is measurable cheaply: count chunks whose text does not end in `.?!`).

## JsoupDocumentReader defaults, and what the default configuration throws away

### Takeaway
`JsoupDocumentReaderConfig.builder()` defaults are **`charset "UTF-8"`, `selector "body"`, `separator "\n"`, `allElements false`, `groupByElement false`, `includeLinkUrls false`, `metadataTags ["description", "keywords"]`, `additionalMetadata {}`**. With only `additionalMetadata(...)` set, the reader produces **exactly one Document per HTML resource**, whose text is `doc.select("body")` → `Element.text()` — the whole body flattened into a **single whitespace-normalised line**. Element ids, classes, every attribute, `href`s, `alt` text, heading levels, table/row/cell structure, list structure and all newlines are **gone**; the configured `separator` is never even used.

### Cited Findings
- `document-readers/spring-ai-jsoup-document-reader/src/main/java/org/springframework/ai/reader/jsoup/config/JsoupDocumentReaderConfig.java`, builder field initialisers verbatim: `charset = "UTF-8"`, `selector = "body"`, `separator = "\n"`, `allElements = false`, `includeLinkUrls = false`, `metadataTags = new ArrayList<>(List.of("description", "keywords"))`, `groupByElement = false`, `additionalMetadata = new HashMap<>()` — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/document-readers/spring-ai-jsoup-document-reader/src/main/java/org/springframework/ai/reader/jsoup/config/JsoupDocumentReaderConfig.java)
- `JsoupDocumentReaderConfig.defaultConfig()` is literally `builder().build()`, and `new JsoupDocumentReader(Resource)` uses it — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/document-readers/spring-ai-jsoup-document-reader/src/main/java/org/springframework/ai/reader/jsoup/JsoupDocumentReader.java)
- Three mutually exclusive read paths in `get()`, in priority order: `allElements` → `doc.body().text()` as one Document; else `groupByElement` → one Document per `doc.select(selector)` match; else (**the default**) → `doc.select(selector)` mapped through `Element::text` and `Collectors.joining(separator)` into **one** Document — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/document-readers/spring-ai-jsoup-document-reader/src/main/java/org/springframework/ai/reader/jsoup/JsoupDocumentReader.java)
- Parsing is `Jsoup.parse(inputStream, this.config.charset, "")` — the **baseUri is the empty string**. `addMetadata` resolves links with `link.attr("abs:href")`, which needs a base URI, so even with `includeLinkUrls(true)` relative hrefs cannot be absolutised — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/document-readers/spring-ai-jsoup-document-reader/src/main/java/org/springframework/ai/reader/jsoup/JsoupDocumentReader.java)
- Metadata always written: `metadata.put("title", jsoupDoc.title())`; then, for each of `metadataTags`, `jsoupDoc.select("meta[name=" + metaTag + "]").attr("content")` is added **only if non-empty**; then `metadata.putAll(this.config.additionalMetadata)` — so `additionalMetadata` **overwrites** `title`/`description`/`keywords` on key collision — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/document-readers/spring-ai-jsoup-document-reader/src/main/java/org/springframework/ai/reader/jsoup/JsoupDocumentReader.java)
- Calling `additionalMetadata(Map)` **replaces** the builder's map; `additionalMetadata(String, Object)` adds to it. Neither touches `metadataTags`, so `["description","keywords"]` stays in force — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/document-readers/spring-ai-jsoup-document-reader/src/main/java/org/springframework/ai/reader/jsoup/config/JsoupDocumentReaderConfig.java)
- `IOException` is wrapped as `new RuntimeException("Failed to read HTML resource: " + resource, e)` — unchecked, with no Spring exception type — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/document-readers/spring-ai-jsoup-document-reader/src/main/java/org/springframework/ai/reader/jsoup/JsoupDocumentReader.java)
- These defaults **are** documented, matching the source: charset "defaults to UTF-8", selector "defaults to body", separator "defaults to \n", `allElements`/`groupByElement`/`includeLinkUrls` "defaults to false", `metadataTags` "defaults to [description, keywords]" — [docs.spring.io ETL Pipeline (page served as 2.0.2)](https://docs.spring.io/spring-ai/reference/api/etl-pipeline.html). What is **not** documented is that the default `selector "body"` matches exactly one element, making `separator` dead and the output a single Document — read from source.
- **Empirical probe** (run locally, jsoup **1.22.2** — the version declared by `spring-ai-jsoup-document-reader-2.0.1.pom` — on a representative HTML fragment with an `id`, a class, `<b>`, `<br>`, a 3-row table, a `<ul>`, an `<a href>`, an `<img alt>`, `<script>`, `<style>` and a `hidden` div). `doc.select("body")` returned **1** element and both the default path and `allElements` path produced the identical single line:
  `Item 7. MD&A Revenue rose 12%. Costs fell. Year Revenue 2024 1,000 2023 900 First Second next page hidden div text`
  while `body().wholeText()` preserved the newlines: `\nItem 7. MD&A\nRevenue rose 12%.\nCosts fell.\nYearRevenue\n20241,000\n2023900\nFirstSecond\nnext page\n\n\nhidden div text\n`. Observed, concretely: no newlines survive `text()`; `<br>` becomes a space; table cells are space-joined with no row or column marker; `<li>`s are space-joined; `id`/`class`/`href`/`src` and `alt` text are absent; `<script>` and `<style>` bodies are excluded; `hidden` content **is** included; `&amp;` is decoded. — local probe against jsoup 1.22.2; `text()` semantics per [jsoup Element.text() javadoc](https://jsoup.org/apidocs/org/jsoup/nodes/Element.html#text())

### Inferences
- **The default config is lossy in a way that compounds with the splitter.** Because `Element.text()` emits no newlines, the splitter's `'\n'` punctuation mark can never fire on this content; only `.`, `?`, `!` can serve as backtrack points. For a page that is mostly tables or figures (no sentence punctuation after char 350), chunk boundaries land at the raw 800th token.
- **Tables are destroyed, not merely degraded.** `Year Revenue 2024 1,000 2023 900` has lost the cell-to-header association entirely; a retrieved chunk can carry a number with no recoverable row/column label. For a financial corpus this is the single largest default-induced loss in the ingestion path, and it happens before chunking, embedding, or retrieval can do anything about it.
- **Section structure is unrecoverable downstream.** `id="item7"` and the `<h1>` level are both discarded, so "which section did this chunk come from" cannot be answered from the Document at all — only `title` (the `<title>` tag) plus whatever `additionalMetadata` the caller injects survives. Switching to `groupByElement(true)` with a section selector, or reading `wholeText()`, is the mechanical fix; the reader exposes neither `wholeText` nor per-element metadata (the source comments that element metadata is deliberately not added, "to avoid duplication").
- `hidden`/off-screen boilerplate being included means nav chrome, cookie banners and print-only variants are embedded as corpus text under the default config.

### Gaps
- I did not verify against this project's actual HTML corpus which of these losses bite hardest (e.g. how much of the corpus is tabular). The probe establishes the mechanism, not the magnitude.
- jsoup's `text()` block-separation behaviour has changed across jsoup minor versions in the past; my probe pins 1.22.2 only. If the project's resolved jsoup ever differs from the 1.22.2 the 2.0.1 POM declares, re-run the probe.

## BatchingStrategy: the default implementation, the real token limit, the tokenizer, and the over-limit behaviour

### Takeaway
The only `BatchingStrategy` implementation shipped in Spring AI 2.0.1's `spring-ai-model` is **`TokenCountBatchingStrategy`**, whose no-arg constructor is `CL100K_BASE`, `maxInputTokenCount = 8191`, `reservePercentage = 0.1` → an **effective limit of 7372 tokens per batch** (the class javadoc says 7371 — it is wrong). A **single document over the limit throws `IllegalArgumentException`** — it is never split and never dropped. Counting is done with JTokkit CL100K_BASE on the *formatted* content, with `MetadataMode.NONE` and `Document.DEFAULT_CONTENT_FORMATTER`.

### Cited Findings
- `spring-ai-model/src/main/java/org/springframework/ai/embedding/TokenCountBatchingStrategy.java`, verbatim: `private static final int MAX_INPUT_TOKEN_COUNT = 8191;` with the comment "Using openai upper limit of input token count as the default."; `private static final double DEFAULT_TOKEN_COUNT_RESERVE_PERCENTAGE = 0.1;`; `public TokenCountBatchingStrategy() { this(EncodingType.CL100K_BASE, MAX_INPUT_TOKEN_COUNT, DEFAULT_TOKEN_COUNT_RESERVE_PERCENTAGE); }` — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/spring-ai-model/src/main/java/org/springframework/ai/embedding/TokenCountBatchingStrategy.java)
- So **yes, 8191** — and it is explicitly OpenAI's `text-embedding-*` input limit, not anything to do with the configured model. The class javadoc links `https://platform.openai.com/docs/guides/embeddings#embedding-models` — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/spring-ai-model/src/main/java/org/springframework/ai/embedding/TokenCountBatchingStrategy.java)
- Effective limit: `this.maxInputTokenCount = (int) Math.round(maxInputTokenCount * (1 - reservePercentage));` → `Math.round(8191 * 0.9)` = `Math.round(7371.900000000001)` = **7372**. The javadoc in the same file states "with the default reserve percentage of 10% (0.1) and the default max input token count of 8191, the actual max input token count used will be 7371" — off by one; the same wording and the same `Math.round` were already present in 1.0.0 — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/spring-ai-model/src/main/java/org/springframework/ai/embedding/TokenCountBatchingStrategy.java); [GitHub v1.0.0](https://github.com/spring-projects/spring-ai/blob/v1.0.0/spring-ai-commons/src/main/java/org/springframework/ai/embedding/TokenCountBatchingStrategy.java)
- Tokenizer: `this.tokenCountEstimator = new JTokkitTokenCountEstimator(encodingType)`, i.e. JTokkit (`jtokkit 1.1.0` resolved), `Encoding.countTokens(text)`, default `CL100K_BASE` — `spring-ai-commons/src/main/java/org/springframework/ai/tokenizer/JTokkitTokenCountEstimator.java` — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/spring-ai-commons/src/main/java/org/springframework/ai/tokenizer/JTokkitTokenCountEstimator.java)
- What is counted: `document.getFormattedContent(this.contentFormatter, this.metadataMode)` with the no-arg-constructor defaults `Document.DEFAULT_CONTENT_FORMATTER` and `MetadataMode.NONE` — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/spring-ai-model/src/main/java/org/springframework/ai/embedding/TokenCountBatchingStrategy.java)
- Over-limit behaviour, verbatim:
  ```java
  int tokenCount = this.tokenCountEstimator
      .estimate(document.getFormattedContent(this.contentFormatter, this.metadataMode));
  if (tokenCount > this.maxInputTokenCount) {
      throw new IllegalArgumentException(
              "Tokens in a single document exceeds the maximum number of allowed input tokens");
  }
  currentSize += tokenCount;
  if (currentSize > this.maxInputTokenCount) {
      batches.add(currentBatch);
      currentBatch = new ArrayList<>();
      currentSize = tokenCount;
  }
  currentBatch.add(document);
  ```
  — i.e. **exception, not split and not dropped**; batching itself is a single greedy pass that preserves input order — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/spring-ai-model/src/main/java/org/springframework/ai/embedding/TokenCountBatchingStrategy.java)
- The consuming default method `EmbeddingModel.embed(List<Document>, EmbeddingOptions, BatchingStrategy)` calls `batchingStrategy.batch(documents)`, then for each sub-batch sends `subBatch.stream().map(this::getEmbeddingContent)`; `getEmbeddingContent` defaults to `document.getText()` and **`OllamaEmbeddingModel` does not override it** (no override exists anywhere in the 2.0.1 modules on disk). It finishes with `Assert.isTrue(embeddings.size() == documents.size(), "Embeddings must have the same number as that of the documents")` — `spring-ai-model/src/main/java/org/springframework/ai/embedding/EmbeddingModel.java` — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/spring-ai-model/src/main/java/org/springframework/ai/embedding/EmbeddingModel.java)
- **Counting mismatch, from source:** the batcher counts `getFormattedContent(formatter, MetadataMode.NONE)` but the embedder sends `getText()`. With `MetadataMode.NONE` and the default formatter these are the same text for a text-only Document, but they are *different call paths*, so any future `ContentFormatter`/`MetadataMode` change makes the batch budget and the payload diverge — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/spring-ai-model/src/main/java/org/springframework/ai/embedding/TokenCountBatchingStrategy.java); [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/spring-ai-model/src/main/java/org/springframework/ai/embedding/EmbeddingModel.java)
- **No auto-configured `BatchingStrategy` bean exists in the modules this project resolves**: scanning every `org.springframework.ai:*:2.0.1` jar in the Gradle cache for class names containing "Batching" found only `spring-ai-model-2.0.1.jar` → `embedding/BatchingStrategy.class` and `embedding/TokenCountBatchingStrategy.class`. The "default implementation" therefore has to be instantiated by the caller — local jar scan of `~/.gradle/caches/.../org.springframework.ai/*/2.0.1/*.jar`
- The 2.0.x reference **ETL page says nothing** about `BatchingStrategy`, `TokenCountBatchingStrategy`, 8191, the reserve percentage, or over-limit behaviour — all of the above is source-read — [docs.spring.io ETL Pipeline (page served as 2.0.2)](https://docs.spring.io/spring-ai/reference/api/etl-pipeline.html)

### Inferences
- **The limit protects an OpenAI budget this project does not have, and does not protect the limit it does have.** 7372 CL100K tokens per *batch* bears no relation to the Ollama model's per-*input* context length. A corpus of 800-token chunks packs ~9 chunks per batch; each individual chunk is far under 7372, so the batcher will never object — while every one of those chunks can still exceed the serving embedding model's context (e.g. 512 tokens for `mxbai-embed-large`). The guard rail is in the wrong dimension.
- **The 7372 exception is a hard ingestion stop with a non-actionable message.** It names neither the document, nor its id, nor its token count. The realistic trigger in this project is not a normal chunk but the `maxNumChunks` overflow chunk described above, or an un-split Document fed straight to `embed(...)`.
- Because `embed(...)` ends in an `Assert` on count equality, any strategy that loses a document surfaces as an opaque `IllegalArgumentException` from the assert rather than as a drop — which is how the 1.x map-keyed bug (next section) would have presented.

### Gaps
- Whether some *other* Spring AI 2.0.1 module (e.g. a vector-store autoconfiguration this project does not depend on) declares a `@Bean BatchingStrategy` default is unverified — I only scanned the jars present in the local cache. For this project, no such bean is on the classpath.
- I did not find a reference-doc page in 2.0.x that documents `BatchingStrategy` defaults at all, so "undocumented" is a negative result from the ETL page plus the absence of any batching content there; I did not exhaustively crawl every docs page.

## Ollama embedding options: what `truncate(false)` guarantees, `num_ctx`, and `keep_alive`

### Takeaway
`OllamaEmbeddingOptions.builder().model(x).truncate(false).build()` sends **exactly** `{"model": x, "input": [...], "truncate": false, "options": {}}` to `POST /api/embed`. Every other option — **`num_ctx` included** — is `null` by default and is simply **omitted**, so Ollama's own defaults apply. Spring AI **does pass `num_ctx` through** (as `options.num_ctx`) *if you set it programmatically*, but in 2.0.1 there is **no configuration property for it on the embedding side at all** (only `model`, `truncate`, `keep-alive` are bound) — the reference docs' `spring.ai.ollama.embedding.num-ctx = 2048` row does not correspond to any bindable property in 2.0.1. On current Ollama, `truncate: false` **does** convert over-length input into an HTTP 400 rather than silent truncation — but it does not raise the limit, and the limit it enforces is `min(effective num_ctx, the model's own context_length)`, which for small embedding models is the model's number.

### Cited Findings
- `OllamaEmbeddingOptions` builder fields are **all `@Nullable` with no initialiser** — `model`, `keepAlive`, `dimensions`, `truncate`, `useNUMA`, `numCtx`, `numBatch`, `numGPU`, `mainGPU`, `lowVRAM`, `f16KV`, `logitsAll`, `vocabOnly`, `useMMap`, `useMLock`, `numThread`. The only defaulting is in the constructor: `this.model = model != null ? model : OllamaModel.MXBAI_EMBED_LARGE.id();` — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/models/spring-ai-ollama/src/main/java/org/springframework/ai/ollama/api/OllamaEmbeddingOptions.java)
- The field javadoc in 2.0.1 states `truncate` "Truncates the end of each input to fit within context length. Returns error if false and context length is exceeded. **Defaults to true**", `numCtx` "Sets the size of the context window used to generate the next token. (Default: 2048)", `numBatch` "(Default: 512)" — these parenthetical "(Default: …)" values are **Ollama's documented defaults, not values Spring AI sends**; the Java fields are null — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/models/spring-ai-ollama/src/main/java/org/springframework/ai/ollama/api/OllamaEmbeddingOptions.java)
- `toMap()` adds each entry **only when non-null** (`if (this.numCtx != null) map.put("num_ctx", this.numCtx);` etc.), and `NON_SUPPORTED_FIELDS = List.of("model", "keep_alive", "truncate", "dimensions")` are filtered back out by `filterNonSupportedFields` because they are top-level request fields — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/models/spring-ai-ollama/src/main/java/org/springframework/ai/ollama/api/OllamaEmbeddingOptions.java)
- Request assembly, verbatim: `new OllamaApi.EmbeddingsRequest(model, embeddingRequest.getInstructions(), requestOptions.getKeepAlive(), OllamaEmbeddingOptions.filterNonSupportedFields(requestOptions.toMap()), requestOptions.getTruncate(), requestOptions.getDimensions())` — `models/spring-ai-ollama/src/main/java/org/springframework/ai/ollama/OllamaEmbeddingModel.java` — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/models/spring-ai-ollama/src/main/java/org/springframework/ai/ollama/OllamaEmbeddingModel.java)
- Wire format: `@JsonInclude(Include.NON_NULL) public record EmbeddingsRequest(@JsonProperty("model") String model, @JsonProperty("input") List<String> input, @JsonProperty("keep_alive") @Nullable String keepAlive, @JsonProperty("options") @Nullable Map<String, Object> options, @JsonProperty("truncate") @Nullable Boolean truncate, @JsonProperty("dimensions") @Nullable Integer dimensions)`, posted to `"/api/embed"` — `models/spring-ai-ollama/src/main/java/org/springframework/ai/ollama/api/OllamaApi.java` — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/models/spring-ai-ollama/src/main/java/org/springframework/ai/ollama/api/OllamaApi.java)
- So with `model` + `truncate(false)` only: `keep_alive` is `null` → **omitted**; the options map is non-null but **empty** after filtering → `"options":{}`; `dimensions` omitted. `truncate:false` *is* sent (it is non-null) — derived from the three source files above — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/models/spring-ai-ollama/src/main/java/org/springframework/ai/ollama/OllamaEmbeddingModel.java)
- Per-request merge (`mergeOptions`) uses `ModelOptionsUtils.mergeOption(runtime, default)` field by field and *only* reads Ollama-specific fields when the runtime options are an `OllamaEmbeddingOptions`; a plain `EmbeddingOptions` contributes only `model` and `dimensions` — so passing generic options at call time **silently discards `truncate`/`numCtx`/`keepAlive`** — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/models/spring-ai-ollama/src/main/java/org/springframework/ai/ollama/OllamaEmbeddingModel.java)
- **Ollama's API contract**: for `POST /api/embed`, `truncate` "truncates the end of each input to fit within context length"; if `false` and the context length is exceeded it "Returns error"; "Defaults to `true`". `keep_alive` "Controls how long the model will stay loaded into memory following the request", default `5m`. The page does **not** discuss `num_ctx` for embeddings — [ollama/docs/api.md](https://github.com/ollama/ollama/blob/main/docs/api.md)
- **Ollama's server source** (`server/routes.go`, `EmbedHandler`, fetched 2026-10-27) computes the per-input limit as the model's own context length, *clamped by* `num_ctx` when one is supplied:
  ```go
  ctxLen := int(m.metadata.Int("context_length"))
  if ctxLen == 0 && m.Config.ModelFormat == "safetensors" { ctxLen = m.Config.ContextLen }
  if opts.NumCtx > 0 { ctxLen = min(opts.NumCtx, ctxLen) }
  ```
  — [ollama/server/routes.go](https://github.com/ollama/ollama/blob/main/server/routes.go)
- And it branches on `truncate` **explicitly**:
  ```go
  if req.Truncate != nil && !*req.Truncate {
      tokens, ctxLen, err := inputTokensAndContext(text)
      ...
      if len(tokens) > ctxLen {
          return nil, 0, api.StatusError{ StatusCode: http.StatusBadRequest,
              ErrorMessage: "the input length exceeds the context length" }

  ```
  The truncating branch returns no warning to the caller — the `bool` "was truncated" result is discarded. With `truncate:false`, the runner-413 retry path is also skipped (`if req.Truncate != nil && !*req.Truncate { return nil, 0, err }`) — [ollama/server/routes.go](https://github.com/ollama/ollama/blob/main/server/routes.go)
- Where the effective `num_ctx` comes from when the request omits it: `opts := api.DefaultOptions(); if opts.NumCtx == 0 { opts.NumCtx = s.defaultNumCtx }`, with `api.DefaultOptions()` setting `NumCtx: int(envconfig.ContextLength())` (i.e. `OLLAMA_CONTEXT_LENGTH`, 0 when unset) and `s.defaultNumCtx` chosen by VRAM tier at server start: `>= 47 GiB → 262144`, `>= 23 GiB → 32768`, otherwise **4096** — [ollama/server/routes.go](https://github.com/ollama/ollama/blob/main/server/routes.go); [ollama/api/types.go](https://github.com/ollama/ollama/blob/main/api/types.go)

- **Spring AI 2.0.1 binds only three embedding properties.** `OllamaEmbeddingProperties` has exactly `model`, `truncate`, `keepAlive` fields plus a `@Deprecated(since = "2.0.0", forRemoval = true)` inner `Options` class that forwards only those same three; `toOptions()` is `OllamaEmbeddingOptions.builder().model(model).truncate(truncate).keepAlive(keepAlive).build()` — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/auto-configurations/models/spring-ai-autoconfigure-model-ollama/src/main/java/org/springframework/ai/model/ollama/autoconfigure/OllamaEmbeddingProperties.java)
- Confirmed from the **shipped metadata** inside `spring-ai-autoconfigure-model-ollama-2.0.1.jar` → `META-INF/spring-configuration-metadata.json`: the only `spring.ai.ollama.embedding.*` properties are `keep-alive`, `model`, `truncate`, `options.keep-alive`, `options.model`, `options.truncate`. There is **no** `spring.ai.ollama.embedding.num-ctx` — local inspection of the published jar
- **This contradicts the reference docs**, which still list a full Ollama options table for embeddings including `spring.ai.ollama.embedding.num-ctx` default `2048`, `num-batch` `512`, `temperature` `0.8`, `top-k` `40`, and so on — properties that are not bindable in 2.0.1 and would be silently ignored by relaxed binding — [docs.spring.io Ollama Embeddings (page served as 2.0.2)](https://docs.spring.io/spring-ai/reference/api/embeddings/ollama-embeddings.html); contradicted by [GitHub v2.0.1 OllamaEmbeddingProperties](https://github.com/spring-projects/spring-ai/blob/v2.0.1/auto-configurations/models/spring-ai-autoconfigure-model-ollama/src/main/java/org/springframework/ai/model/ollama/autoconfigure/OllamaEmbeddingProperties.java) and by the jar's own configuration metadata
- The same docs page also documents `spring.ai.ollama.embedding.model` default `mxbai-embed-large` and `keep_alive` default `5m`, and is internally inconsistent about the builder method name (`.truncates(false)` in one snippet, `.truncate(false)` in another) — [docs.spring.io Ollama Embeddings](https://docs.spring.io/spring-ai/reference/api/embeddings/ollama-embeddings.html)

### Inferences
- **What `truncate(false)` guarantees:** that *Ollama* will refuse (HTTP 400, `"the input length exceeds the context length"`) rather than silently embed a prefix, on a current Ollama server, for the plain-text path. Spring AI's `RestClient` surfaces that as a thrown client-error exception, so the ingestion run fails loudly instead of writing a quietly-truncated vector. On that reading, the project's `truncate(false)` **does** guard against silent `num_ctx` truncation — the premise that it does not is, for current Ollama, not borne out by the server source.
- **What it does not guarantee:** (1) it does not set or raise any limit — the limit remains `min(effective num_ctx, model context_length) - BOS/EOS`, and for small embedding models (e.g. `mxbai-embed-large`, 512; `nomic-embed-text`, 2048) the **model's** number binds, not the 4096 server default; (2) it is a per-request flag with no client-side check, so Spring AI never knows the limit and cannot pre-validate; (3) the failure arrives mid-ingestion as an HTTP error on one batch, after earlier batches have already been written — the project gets a partially-populated store unless it is transactional; (4) it says nothing about `num_batch` physical-batch clamps, where the runner's own 413 is returned unchanged; (5) nothing stops a *future or older* Ollama, or a proxy, from ignoring the flag.
- **The 800-token default collides with this directly.** 800 CL100K tokens is typically more than 512 tokens of any embedding model's own tokenizer, so a `mxbai-embed-large`-class model plus `truncate(false)` is a configuration that *fails* on the first long chunk; the same corpus with `truncate(true)` would instead embed roughly the first 512 tokens of each 800-token chunk and lose the rest invisibly. Either way the chunk size, not the flag, is the defect.
- **`num_ctx` is passed through, never set.** Spring AI is not "ignoring" it — `toMap()` → `options.num_ctx` is the designed path — but in 2.0.1 the only way to set it for embeddings is programmatically on `OllamaEmbeddingOptions`, because the property was dropped in the 2.0 properties rewrite. Any `application.yaml` entry such as `spring.ai.ollama.embedding.num-ctx: 8192` written from the docs is **dead configuration** in 2.0.1: relaxed binding ignores unknown keys under the prefix, so it fails silently.
- **`keep_alive` is likewise unset**, so Ollama's `5m` applies: the embedding model unloads 5 minutes after the last request and the next ingestion run pays a cold model load (and can race a chat model for VRAM). Setting `keep_alive` for a long ingestion run is a one-line, measurable win; it *is* bindable in 2.0.1 (`spring.ai.ollama.embedding.keep-alive`).
- `dimensions` is also null by default, so no dimension request is sent; the vector width is whatever the model returns, and `AbstractEmbeddingModel.dimensions()` discovers it by embedding the literal string `"Test String"` (`EmbeddingModel.dimensions()` default) — a live call on first use.

### Gaps
- The `routes.go` / `api/types.go` behaviour above is Ollama **`main` as of 2026-10-27**. Web search surfaced only second-hand community reports (GitHub issue summaries, forum posts) claiming that older Ollama versions silently truncated embeddings or honoured `truncate` inconsistently; I could not open a primary source for any of them, so they are recorded here as unverified. The guarantee is therefore **version-dependent** and should be pinned against the Ollama version this project actually runs (`ollama --version`, then the matching tag's `server/routes.go`). I could not find an official Ollama changelog entry stating when embed-side `truncate` enforcement reached its current form.
- The exact `context_length` in the GGUF metadata of the specific embedding model this project uses is not stated anywhere in Spring AI; it must be read from `ollama show <model>`. I did not have the model name/registry metadata to verify, so the "512 for `mxbai-embed-large`" figure above is cited as a widely-reported model property and should be confirmed with `ollama show`.
- I did not capture a real HTTP request body on the wire (no running Ollama in this session); the `{"model":…,"input":[…],"truncate":false,"options":{}}` shape is derived from the record's Jackson annotations plus `filterNonSupportedFields`, not observed.

## What changed in this surface between Spring AI 1.x and 2.0.x

### Takeaway
The **values** of the headline defaults did not move — 800/350/5/10000/true, CL100K_BASE, 8191 + 10% reserve, jsoup `body`/UTF-8 are all unchanged since 1.0.0. What changed is the **plumbing and two real behaviours**: `TokenTextSplitter` gained configurable encoding and punctuation marks and now **skips punctuation backtracking when the text fits in one chunk**; `TokenCountBatchingStrategy` moved module and had a **silent duplicate-document drop fixed**; `OllamaOptions` was split into `OllamaChatOptions`/`OllamaEmbeddingOptions` and the Ollama **embedding properties were reduced to `model`/`truncate`/`keep-alive`**, removing `num_ctx` (and the rest) from configuration.

### Cited Findings
- `TokenTextSplitter` 1.0.0 vs 2.0.1: 1.0.0 hard-codes `private final Encoding encoding = this.registry.getEncoding(EncodingType.CL100K_BASE);` and inlines the punctuation set as `Math.max(chunkText.lastIndexOf('.'), Math.max(chunkText.lastIndexOf('?'), Math.max(chunkText.lastIndexOf('!'), chunkText.lastIndexOf('\n'))))`; 2.0.1 adds `DEFAULT_ENCODING_TYPE`/`withEncodingType` and `DEFAULT_PUNCTUATION_MARKS`/`withPunctuationMarks` with the same effective values — [GitHub v1.0.0](https://github.com/spring-projects/spring-ai/blob/v1.0.0/spring-ai-commons/src/main/java/org/springframework/ai/transformer/splitter/TokenTextSplitter.java); [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/spring-ai-commons/src/main/java/org/springframework/ai/transformer/splitter/TokenTextSplitter.java)
- **Behaviour change in `doSplit`:** 1.0.0 applied the punctuation backtrack **unconditionally**; 2.0.1 wraps it in `if (tokens.size() > chunkSize)` and documents it in the method javadoc: "Punctuation-based splitting only applies when the token count exceeds the chunk size (`tokens.size() > chunkSize`). Text that exactly matches or is smaller than the chunk size is returned as a single chunk without punctuation-based truncation." — [GitHub v1.0.0](https://github.com/spring-projects/spring-ai/blob/v1.0.0/spring-ai-commons/src/main/java/org/springframework/ai/transformer/splitter/TokenTextSplitter.java); [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/spring-ai-commons/src/main/java/org/springframework/ai/transformer/splitter/TokenTextSplitter.java)

- `BatchingStrategy`/`TokenCountBatchingStrategy` **moved module**: `spring-ai-commons/.../org/springframework/ai/embedding/` in 1.0.0 → `spring-ai-model/.../org/springframework/ai/embedding/` in 2.0.1 (package unchanged) — [GitHub v1.0.0 tree](https://github.com/spring-projects/spring-ai/blob/v1.0.0/spring-ai-commons/src/main/java/org/springframework/ai/embedding/TokenCountBatchingStrategy.java); [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/spring-ai-model/src/main/java/org/springframework/ai/embedding/TokenCountBatchingStrategy.java)
- **Bug fix with a behavioural consequence:** 1.0.0 accumulated into `Map<Document, Integer> documentTokens = new LinkedHashMap<>();` before batching; 2.0.1 iterates the list directly and says so in a code comment: "Do not collect the documents into a Map keyed by Document: equal documents would collapse to a single entry and be silently dropped from the batches." (`Document.equals` compares id, text, media, metadata and score.) — [GitHub v1.0.0](https://github.com/spring-projects/spring-ai/blob/v1.0.0/spring-ai-commons/src/main/java/org/springframework/ai/embedding/TokenCountBatchingStrategy.java); [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/spring-ai-model/src/main/java/org/springframework/ai/embedding/TokenCountBatchingStrategy.java)
- The `8191` constant, the `0.1` reserve, the `Math.round` arithmetic and the over-limit `IllegalArgumentException` message are **identical** in 1.0.0 and 2.0.1 — [GitHub v1.0.0](https://github.com/spring-projects/spring-ai/blob/v1.0.0/spring-ai-commons/src/main/java/org/springframework/ai/embedding/TokenCountBatchingStrategy.java)
- **Ollama options split:** 1.0.0 had one `OllamaOptions` used for chat *and* embeddings, and `OllamaEmbeddingProperties` held it whole: `@NestedConfigurationProperty private OllamaOptions options = OllamaOptions.builder().model(OllamaModel.MXBAI_EMBED_LARGE.id()).build();` — so in 1.x **every** Ollama option, `num_ctx` included, was bindable under `spring.ai.ollama.embedding.options.*`. 2.0.1 ships separate `OllamaChatOptions` and `OllamaEmbeddingOptions`, and `OllamaEmbeddingProperties` exposes only `model`, `truncate`, `keep-alive` (with `options.*` deprecated `since = "2.0.0"`), which the shipped `spring-configuration-metadata.json` confirms — [GitHub v1.0.0](https://github.com/spring-projects/spring-ai/blob/v1.0.0/auto-configurations/models/spring-ai-autoconfigure-model-ollama/src/main/java/org/springframework/ai/model/ollama/autoconfigure/OllamaEmbeddingProperties.java); [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/auto-configurations/models/spring-ai-autoconfigure-model-ollama/src/main/java/org/springframework/ai/model/ollama/autoconfigure/OllamaEmbeddingProperties.java)
- 2.0.1 `OllamaEmbeddingOptions` also adds a `dimensions` field (top-level `dimensions` on the `/api/embed` request) that 1.x did not send — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/models/spring-ai-ollama/src/main/java/org/springframework/ai/ollama/api/OllamaEmbeddingOptions.java)
- `EmbeddingModel` in 2.0.1 adds a `getEmbeddingContent(Document)` hook (defaulting to `getText()`) used by the batching `embed(...)` overload; no Ollama override exists, so Ollama embeddings never include metadata — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/spring-ai-model/src/main/java/org/springframework/ai/embedding/EmbeddingModel.java)
- `JsoupDocumentReaderConfig` defaults are unchanged between 1.x and 2.0.1 as far as this comparison goes (all seven builder initialisers identical in the 2.0.1 source; the class still exposes public final fields rather than getters) — [GitHub v2.0.1](https://github.com/spring-projects/spring-ai/blob/v2.0.1/document-readers/spring-ai-jsoup-document-reader/src/main/java/org/springframework/ai/reader/jsoup/config/JsoupDocumentReaderConfig.java)

### Inferences
- For an audit spanning three articles: **nothing in the published numbers needs retracting** — 800/350/5/10000 and 8191/10% were the same in the 1.x the earlier episodes may have been written against. The claims that *would* need a version qualifier are (a) "small texts are split at the last punctuation mark" (true pre-2.0, false in 2.0.1), (b) anything showing `spring.ai.ollama.embedding.options.num-ctx` in YAML (worked in 1.x, dead in 2.0.1), and (c) `new TokenTextSplitter(...)` constructor usage (deprecated for removal in 2.0.x).

### Gaps
- I did not locate an official Spring AI 2.0 upgrade/release-note page enumerating the `OllamaOptions` split or the embedding-properties reduction; the change is established from the 1.0.0 and 2.0.1 sources plus the `@Deprecated(since = "2.0.0")` markers and shipped configuration metadata. A release-note citation would strengthen it.
- I compared 2.0.1 against **1.0.0** only. If any article was written against 1.1.x, the intermediate 1.1 behaviour (particularly whether the `tokens.size() > chunkSize` guard landed in 1.1.x or only in 2.0) is unverified.
